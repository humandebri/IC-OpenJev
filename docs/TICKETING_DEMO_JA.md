# 日本語チケット判定デモの検証結果

## 判定：公開を保留

日本語を直接判定する既存openJevモデルでは、事前に決めた公開基準を満たしませんでした。計画に従い、画面作成と公開を保留しています。翻訳や別モデルへの切り替えは行っていません。

| 項目 | 評価結果 | 公開基準 |
| --- | --- | --- |
| 担当部署 | 8/24件（33.3%） | 20/24件以上 |
| 優先度 | 9/24件（37.5%） | 20/24件以上 |
| 高優先度の検出 | 8/8件 | 見落としゼロ |
| API成功 | 48/48呼び出し | 全件成功 |

優先度は24件中23件を「高」としました。高優先度の見落としはありませんが、低・通常を区別できていません。入力は34〜48トークンで、現在の52トークン上限に収まりました。今回の不合格は入力超過や通信失敗によるものではありません。

## 実施内容

- 固定した架空の日本語データ：調整用12件、評価用24件。評価用は4部署×3優先度×2件。
- 本番 `decide_query` を匿名で直接呼び、部署・優先度を独立判定。
- 調整用で英語の短い部署名・優先度名を試し、説明的な候補表現も1回比較。部署は最初の表現、優先度は説明的な表現の方が調整用正解数が多かったため、その組み合わせを固定。
- 評価用は固定後に1回だけ実行。結果を見た再調整はしていません。
- 翻訳、入力切り詰め、キーワードによる正解の補正、モデル設定変更は実施していません。

## 成果物と再現

`web/ticketing/src/model.ts` にAPIクライアントと応答検証、`web/ticketing/scripts/study.ts` に実測と合否判定を実装しました。調整用の入力・実装ハッシュと一致しない評価は拒否し、評価不合格では終了コード2を返します。

実行手順は [検証実装のREADME](../web/ticketing/README.md)、入力は [cases.json](../fixtures/ticketing-ja/cases.json)、全評価結果は [evaluation.json](../artifacts/ticketing-ja/evaluation.json) にあります。比較した調整用結果も同じartifactディレクトリに保持しています。入力ファイルの移動時にバイト列は変更していません。

検証基盤の修正後は、実行ごとのフォルダに形式バージョン2の記録を保存し、評価時に指定した調整結果とのモデル・入力・コード・依存関係の一致を確認します。上記の旧記録4件は読み取り用に保持し、新しい評価の調整結果には使用しません。基盤修正に伴う本番APIの再評価は行っておらず、本レポートの8/24件・9/24件という結果と公開保留の判断はそのままです。

初回検証時には型チェックと、候補IDの不整合・不正スコア・モデル不一致・上限超過などのテスト14件が成功しました。画面・公開設定は未作成のため、ブラウザ検証・ビルド・配備は未実施です。基盤修正では、評価条件・参照する調整結果・保存処理を模擬クライアントと一時ディレクトリで検証しています。

## 解釈と次の判断

これは特定のモデルと短い候補表現による、小規模な合成日本語データでの結果です。日本語でのチケット判定一般が不可能という結論ではありません。

現状のまま、日本語の社内問い合わせを自動振り分けできるデモとして公開する根拠は得られませんでした。次に進めるなら、英訳を挟む方式か日本語向けモデルを別の実験として評価します。今回の評価データを今後の調整に使った場合は、新しい評価用データを用意する必要があります。
