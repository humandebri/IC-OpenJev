# IT問い合わせの対応キュー提案

社内問い合わせを部署名で分類するデモとは別に、ITサービスデスクの受付キューと優先度を提案するデモを追加した。チケットは問い合わせの本文と対応状況を管理する業務上の記録を指す。本デモは本文の分類までを扱い、チケットの作成・割り当て・担当者への通知は行わない。

## 分類の範囲

| ID | キュー | 対象 |
|---|---|---|
| account | アカウント・権限 | ID、パスワード、多要素認証、アクセス権の申請 |
| device | 端末・ソフトウェア | PC、周辺機器、アプリの導入・設定・故障 |
| network | ネットワーク・VPN | 回線、Wi-Fi、DNS、VPNの通信障害 |
| review | 要確認 | セキュリティ、IT以外の相談、複数の要件、情報不足 |

VPNの利用権限の申請はaccount、VPNの通信不調はnetworkとする。優先度はlow・normal・highの3段階で、本文にある影響範囲・期限・業務停止の情報から候補を出す。セキュリティ相談を自動処理する専用キューは用意していない。

## モデルと評価

既存の日本語130M INT8エンコーダーを固定し、512次元の特徴量からキュー4クラスと優先度3クラスを求める線形ヘッドだけを追加学習した。既存の重み・部署ヘッド・優先度ヘッドは変更しない。追加ヘッドはJSONで94,326バイト、永続化する数値配列は約14KiBで、130Mモデルを複製しない。

[合成コーパス](../fixtures/ticketing-ja/it-routing/cases.json)は学習96件、検証24件、テスト48件。seed 17・29・43のチェックポイントと確信度・マージンの閾値は検証データだけで選び、テストは合否判定に使った。採用条件は、自動処理候補のキュー・優先度の同時正解率95%以上、対象外相談の要確認への回収100%、対象内の候補採用率50%以上。

2026-11-19の実験 `20261119T025939Z-787eb41c` は**不合格**だった。

| 指標 | 検証 | テスト |
|---|---:|---:|
| キュー正解 | 24/24 | 44/48（91.7%） |
| 優先度正解 | 24/24 | 46/48（95.8%） |
| 閾値を通過した候補の同時正解 | 17/17 | 29/33（87.9%） |
| 対象外相談を要確認に回収 | 6/6 | 11/12 |

選択されたseedは29、閾値はキュー0.8・上位2候補の差0.3・優先度0.9。テストを見て閾値を変更していない。上表は閾値による自動処理を仮定した評価であり、現在のAPIの処理方針とは異なる。

**現在のAPIは全件を担当者確認に回す。** `validated=false` のヘッドは候補に高いスコアが付いても `decision=review`、理由は `validation_failed` となる。初回の実験ヘッドにはvalidatedフィールドがないため、省略時falseとして扱う。画面も候補と最終的な要確認を分けて表示する。スコアは校正済みの正答率ではなく、この小規模な架空データで企業の実データに対する精度は判断できない。

## ローカル実行

既存の日本語INT8パック `models/ticketing-ja/optimized-seed29-v1/int8` を用意する。学習にはPyTorchが必要。以下はリポジトリ直下で実行する。

```sh
cargo build --release --locked -p ticketing-candle --bin ticketing-infer
cargo build --release --locked -p ticketing-runtime --bin it-routing-infer
python3 tools/train_it_ticket_router.py
```

実行ごとに `artifacts/ticketing-ja/it-routing/<UTC時刻＋UUID>/` を新規作成する。既存の計測結果は上書きしない。正常な評価完了でも採用条件に届かない場合の終了コードは2。合格は0、実行異常は1になる。report.jsonにはデータ・コード・モデルのハッシュ、選択条件、評価結果を記録する。

別々のターミナルでローカルAPIと画面を起動する。HEAD_PATHは実験が出力したhead.jsonのパスに置き換える。

```sh
python3 tools/serve_it_ticket_router.py --head HEAD_PATH
```

```sh
cd web/ticketing
pnpm install --frozen-lockfile
pnpm dev
```

`http://127.0.0.1:5173/?local=1` で実際のINT8推論を試せる。ローカルAPIは127.0.0.1:5191だけで待ち受け、Viteが転送する。入力上限は64トークン。`?view=department` は既存の部署分類画面を表示する。local=1の指定がないIT画面は本番canister APIを使用する。

## canisterへの追加

- `it_routing_info`：ヘッドとベースモデルの識別子、準備状況、検証済みフラグ、上限。
- `it_routing_set_head`：所有者だけが呼べるヘッド設定update。JSONのサイズ・形状・有限値・閾値・ベースモデルの一致を検査する。
- `route_it_ticket`：キュー・優先度候補、要確認の理由、実測命令数を返すquery。replicated呼び出しは拒否する。

ヘッドのSHA-256とベースモデルのSHA-256を別々に返す。ベースモデルを変更した場合、古いヘッドは使用できない。既存の `classify_ticket` と `decide_query` は保持する。

永続化は既存スナップショットより前の未使用領域を使う。ヘッダーは48〜64バイト、2スロットは960KiB・992KiBを起点に各32KiB。既存の日本語サイドカーと一次スナップショットには重ならず、それらの状態形式も変更しない。アップグレード時のチェックサム付き保存・復元と、旧Wasmへのロールバック後の復帰をPocketIC統合テストで確認する。

今回のPocketIC検証では、検証・テスト計72件のキュー・優先度候補がネイティブ実装と一致し、全件の要確認を確認した。対象72件の最大実測命令数は1,629,511,271で、4.5Bのquery予算内だった。これは各本文での実測で、全入力についての上限保証ではない。旧APIのCandid互換性、既存部署ヘッドのネイティブ出力の一致も確認した。

Python 93件、UI 90件、対象Rustライブラリ23件のテストとClippyを実行した。UIはvlmkitの表示・文言・横スクロール・ハンドラー・操作・レスポンシブ検査を通過し、実ブラウザでも候補表示、入力変更時の結果破棄、キーボード送信、64トークン超過時の表示と再試行を確認した。操作検査には、入力枠全体のフォーカス表示と空入力時の無効ボタンに関する警告が残るため、キーボードでの到達と操作を別途確認した。
